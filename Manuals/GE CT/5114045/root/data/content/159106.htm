RIP Boot Sequence (MVME-24xx)

1  Motorola Firmware (“PPC4-Bug>” prompt)

  1. Entered after power-on reset.

  2. Can execute board level diagnostics.

  3. RIP does not respond to ping in this state.

  4. RIP can ping other hosts in this state.

  5. RIP cannot reset VME bus in this state.

  6. Transfers control to VxWorks bootrom via romboot (“rb”) command.

  7. Useful commands:

    • rb;v - transfer control to VxWorks bootrom

    • nping 0 0 192.9.220.11 192.9.220.1 1 - ping the OC one time

    • he - help

2  VxWorks bootrom ([VxWorks Boot]: prompt)

  1. RIP does not respond to ping in this state.

  2. RIP can reset the VME bus in this state.

  3. Two commands added by GEMS to menu:

    • b - does a local reset of the board and returns control to Motorola Firmware

    • v - does a VME reset of the ICE chassis and returns control to the Vxworks Bootrom

  4. Boot string is sent by procICE to boot the kernel and transfer control to VxWorks.

3  VxWorks shell (-> prompt)

Functions like a Unix shell but it is not the same.

4  Useful VxWorks Shell Commands

  • ipstatShow - similar to netstat on OC, but shows only IP statistics

  • tcpstatShow - similar to netstat on Unix, but shows only TCP statistics

  • ifShow - Shows information about the Ethernet interface including the MAC address

  • arpShow - Shows the mapping of IP addresses to MAC addresses

  • i - Shows the state of all running tasks (like Unix "ps")

5  Boot Sequence

NOTE:Numbers in the left column of the sample iceConsole.log output (see Table 1) correspond to the numbers in the sequence below:

  1. After power is turned on, RIP goes into Motorola Firmware and waits for input from the serial port.

  2. procICE executes “sbcutil -resetvme” script, which does the following:

    1. Transfers control to the VxWorks bootrom.

    2. Resets the VME bus.

    3. Transfers control back to the VxWorks bootrom.

  3. procICE sends the boot string to the VxWorks bootrom to bring up the system and waits for the RIP applications to reply.

  4. RIP downloads the VxWorks kernel by doing an rsh to the OC as indicated by the “Loading…” message. When it is complete, the number of bytes downloaded is printed on the console.

    1. Note that this normally takes about one second. Network or installation problems can cause the RIP to hang at this point.

    2. When it succeeds you can see the rsh command printed in the Unix syslog on the OC.

  5. Bootrom transfers control to VxWorks operating system.

  6. RIP probes the SCSI bus looking for SCSI devices. All devices present are printed on the console. Note that normally this takes only a couple of seconds. Problems on the SCSI bus can cause the RIP to hang at this point.

  7. RIP creates a proxy network, which allows the IG to boot. The IG cannot download its VxWorks kernel until this happens.

  8. The RIP mounts all exported NFS file systems from the OC. These are printed on the console.

    1. This normally takes only a second or so. Network or installation problems can cause this to hang or fail.

    2. The only indication of failure is that no file systems are printed.

    3. Applications will not start unless the /usr/g filesystem is mounted.

  9. VxWorks downloads the symbol table.

    1. This normally takes less than a second. Network or installation problems can cause this to hang or fail.

    2. When it succeeds you can see the rsh command printed in the Unix syslog on the OC.

    3. Applications cannot start without the symbol table.

  10. RIP monitors IG board waiting for it to boot.

    1. If the IG fails to boot it will reset the IG and try again.

    2. The IG fails to boot on occasion due to glitches in the VxWorks operating system.

    3. If the IG requires more than one retry to boot, or the iceConsole.log file shows many retries, it could indicate a problem with the IG or with the VME backplane.

    4. Successful boot of IG is indicated by “Image Generator is UP” message

    5. When IG boot succeeds you can see the rsh commands printed in the Unix syslog on the OC.

  11. RIP prints out the Pegasus hardware configuration.

  12. RIP downloads CT applications.

  13. RIP applications read the ECOMM database.

  14. RIP applications read the ERMES database. No messages go the gesyslog from the ICE until this succeeds.

  15. Application is started.

  16. Raw data disk is initialized by sdiomgr. Output goes to console.

    This normally takes only a few seconds. A corrupted filesystem or SCSI hardware problems can cause this to hang which will result in a message from vxmonitor indicating that sdiomgr took too long to start up.

  17. This message appears when recon has successfully initialized. It means that the recon subsystem is functioning and ready to make images.
